# 4. Anjali Mishra

## **Role: Backend & Integration Engineer**

### Primary Responsibility

Anjali Mishra's role in RAAHI is centered around the **backend and integration layer**, particularly the flow of information between the Edge processing system and the centralized RAAHI platform.

RAAHI is composed of several independently operating components. The backend layer is what allows these components to communicate as one system.

The relevant flow is:

```text
RAAHI-Eye
   │
   │ Video + GPS
   ▼
RAAHI-Edge
   │
   │ Events + Telemetry + Evidence
   ▼
RAAHI-Central
   │
   ├── Database
   ├── Evidence Storage
   └── Dashboard
```

Anjali's responsibility is primarily within the **backend/data/integration side of this pipeline**.

---

# 4.1 Backend Integration

RAAHI generates information at the Edge that needs to be transferred to the Central platform.

The Edge layer can generate structured observations containing information such as:

- Event ID
- Event type
- Vehicle/bus identity
- Timestamp
- GPS coordinates
- Detection information
- Confidence information
- Evidence references

The backend integration layer provides the infrastructure through which this information can be received, processed, and represented centrally.

This creates the connection between **local Edge intelligence** and **centralized urban intelligence**.

# 4.3 Centralized Event Data

The RAAHI-Central layer provides centralized handling of observations generated by the Edge nodes.

An event can contain multiple pieces of information:

```text
Event
 ├── Event ID
 ├── Vehicle ID
 ├── Event Type
 ├── Timestamp
 ├── Latitude
 ├── Longitude
 ├── Detection Data
 └── Evidence Reference
```

The backend layer is responsible for supporting the movement of this structured information through the Central system.

This allows downstream components such as the GIS dashboard to consume a consistent representation of RAAHI observations.

# 4.4 MongoDB Integration

RAAHI-Central uses **MongoDB Atlas** as part of its centralized data-storage architecture.

The backend layer connects incoming RAAHI information with persistent storage so that observations are not limited to transient API requests.

The conceptual flow is:

```text
Edge Event
    ↓
Central API
    ↓
Validation / Processing
    ↓
MongoDB
    ↓
Persistent RAAHI Record
```

This provides the data foundation required for:

- Event retrieval
- Geographic visualization
- Historical observations
- Spatial correlation
- Transport analytics
- Dashboard presentation

# 4.6 Evidence Integration

RAAHI does not rely exclusively on numerical event metadata.

When an event occurs, the system can generate an associated video evidence clip.

The evidence flow is approximately:

```text
Detection
   ↓
Event
   ↓
Evidence Clip
   ↓

   ↓

   ↓
```

The backend/integration layer needs to preserve the relationship between the structured event and its associated evidence.

This allows an evaluator or operator to move from an event record toward the supporting visual evidence.

# 4.7 Integration With the Offline Edge Queue

RAAHI-Edge incorporates an SQLite-backed offline queue so that temporary network interruptions do not necessarily result in immediate loss of generated events.

The Edge-side lifecycle can be represented as:

```text
RECORDING
    ↓
PENDING
    ↓
IN_FLIGHT
    ↓
SENT
```

The Central backend is the destination toward which events eventually move when connectivity is available.

This gives the complete system a more resilient architecture:

```text
Camera
  ↓
Edge AI
  ↓
Local Queue
  ↓
Network Available?
  │
  ├── No → Keep locally
  │
  └── Yes
        ↓
     Central
```

The backend therefore forms part of a system designed for real-world mobile connectivity rather than assuming a permanently perfect network.

# 4.9 Supporting Deterministic Central Processing

RAAHI-Central intentionally uses deterministic processing for important correlation tasks.

For example, observations can be compared using:

- Geographic distance
- Time windows
- Vehicle identity
- Event type
- Other structured attributes

This is preferable to adding another AI model merely for the sake of having AI everywhere.

The backend/data layer provides the structured information required for these operations.

The resulting architecture can therefore be represented as:

```text
AI at Edge
    ↓
Structured Events
    ↓
Deterministic Central Processing
    ↓
Persistent Data
    ↓
GIS Visualization
```

# 4.10 Multi-Vehicle Data Integration

One of the major goals of RAAHI is to turn public-transport vehicles into distributed sensing nodes.

Instead of relying on one vehicle:

```text
Bus A → Observation
```

the system can scale conceptually toward:

```text
Bus A ──┐
Bus B ──┤
Bus C ──┼──→ Central Backend
Bus D ──┤
Bus E ──┘
```

The backend becomes increasingly important as the number of sensing vehicles increases because observations from multiple buses must be represented within one centralized system.

This provides the foundation for fleet-level analysis.

# 4.14 Reliability Considerations

RAAHI is designed for deployment on moving public-transport vehicles, which introduces real-world connectivity challenges.

The backend architecture therefore works together with the Edge's offline queue to avoid assuming:

> "The internet will always work because obviously it loves us."

Instead:

```text
Edge
 │
 ├── Central reachable
 │       ↓
 │    Send event
 │
 └── Central unavailable
         ↓
      Store locally
         ↓
      Retry later
```

This architecture improves resilience during intermittent connectivity.
